# GOD-Level Research Report: Dynamic Agent Swarm Spawning in AI Coding Tools

**Date**: 2026-06-15
**Topic**: Cursor agent swarm patterns & dynamic sub-agent spawning throughout workflows
**Context**: dreamcode/open code sensor-gate re-dispatch issue (specialists respawn every turn)

---

## Executive Summary

**The core finding is confirmed: Cursor, Claude Code, and every major AI coding tool faces the same architectural challenge — preventing agent re-spawn on every user turn.** The industry solution is a **session-level dispatch cache** combined with **workflow-driven recall**, not a static step counter.

Three key patterns emerge:
1. **Hub-and-spoke orchestration** with a deterministic workflow engine controlling agent spawning (not agents self-spawning)
2. **Session-level state tracking** — every production system uses persistent session-level flags, not in-memory step counters
3. **Cost-gated spawning** — sub-agents should only spawn when the subtask exceeds ~10k input tokens; below that, isolation isn't worth the overhead

The dreamcode sensor-gate bug (`step === 1` guard resetting per runLoop invocation) is a well-known anti-pattern that every tool has solved. Cursor uses `.cursor/agents/` declarations + always-applied rules. Claude Code uses session-level deferral. The fix is straightforward: **track dispatch in SessionRunState**, not in a local `step` variable.

## Findings by Vector

### Vector 1: Cursor Agent Architecture — Sub-agent Spawning Internals 🟢 HIGH Confidence

#### Key Facts

1. **Custom sub-agents are defined as markdown files** in Cursor's `agents/` and `skills/` directories, with frontmatter like `name`, `description`, `model`, `readonly`, `is_background` [1][2]. These create isolated-context specialist agents.

2. **Cursor uses a single-level orchestration pattern**: the main agent spawns role-specific sub-agents directly (Architect → Planner, Implementer, Reviewer, Tester) — NOT a coordinator agent that spawns additional workers [1][3].

3. **Model selection per sub-agent** depends on plan type: legacy request-based plans use fixed models per built-in subagent; token-based plans allow custom subagents to specify a model or `model: inherit` to follow the parent [4].

4. **YOLO mode** (auto-run) is a **permission level for command execution**, distinct from sub-agent spawning. It allows terminal commands without confirmation prompts [5][6].

5. **`.cursorrules` are static, global-scoped rules** — they do NOT provide session-level state tracking or "current phase" awareness. For stateful workflows, Cursor users create explicit markdown state documents (`workflow_state.md`) that the agent reads/updates each loop iteration [7].

6. **Cursor's workflow orchestration uses three distinct concepts** [8]:
   - **Rules** — when behavior applies and hard prohibitions
   - **Skills** — what good looks like (reusable capabilities)
   - **Agents** — multi-step workflows (who loads what, in what order)

> *"Rules decide when a surface is in play; skills decide what good looks like; agents describe the multi-step workflow."* [8]

### Vector 2: Dynamic Agent Swarm Patterns 🟢 HIGH Confidence

#### Key Facts

1. **Three dominant architectural patterns** exist for multi-agent coding systems [1][2]:

| Pattern | Orchestration Locus | Best For | Risk |
|---------|-------------------|----------|------|
| **Hub-and-Spoke** | Central router routes messages, minimal reasoning | Multi-tenant, independent agents sharing data | Single point of failure |
| **Supervisor (Hierarchical)** | Single reasoning orchestrator calls agents | Complex workflows needing judgment | Orchestrator bottleneck |
| **Swarm (Decentralized)** | Emergent, local interactions | Highly parallel independent tasks | Unpredictable costs, debugging hell |

2. **Production guidance strongly favors separating orchestration from execution**. Use deterministic scaffolding (workflow engines like Temporal, AWS Step Functions) for the control flow, and keep LLM non-determinism in isolated "activities" [3][4].

3. **The spawn-resume protocol** is the production-proven pattern for dynamic agent spawning [1]:
   - Parent creates a `SpawnPackage` with: memory slice, selected skills/tools, execution context, task spec, complexity metrics
   - Child runs with isolated context
   - Child returns a `ResumePackage` with: output, diffs, execution trace, learned skills, performance metrics

4. **The cost model for sub-agent spawning** is well-established [5]:
   - Break-even is ~**10,000 input tokens of real work** per sub-agent
   - Tasks under 10k tokens → keep in main agent (isolation doesn't pay off)
   - Overhead should be ≤ ~30% of subtask's total tokens
   - Use cheap models (Haiku-class) for wide reading; use expensive models (Opus-class) only where "judgment compounds"

5. **Never let agents self-spawn recursively** [6]. Multiple production teams report "infinite delegating managers" as the #1 anti-pattern. Cap recursion depth explicitly.

> *"Subagents are often costly overkill except for very large or parallelizable tasks."* — Y Combinator discussion of Claude Code sub-agents [7]

#### Key Insight for dreamcode
The current approach (spawn N specialist Personas on every turn via `Effect.forkIn`) maps to the **Supervisor pattern** but lacks the **session-level dispatch cache**. The `step === 1` guard is an in-memory counter that resets per `runLoop` invocation — not a persistent session-level flag. This is the exact anti-pattern that cost-gated spawning was designed to solve.

#### Confidence: HIGH
Multiple independent sources converge on the same patterns and cost models. No significant disagreements.

### Vector 4: Implementation Architecture for dreamcode 🟢 HIGH Confidence

#### Current Architecture (Problematic)

```
PromptInput → runLoop() {
  let step = 0                    // ← RESETS every invocation
  while (true) {
    step++
    if (step === 1) {             // ← TRUE on every new user message
      sensorGate.classify()       // ← RE-CLASSIFIES every turn
      personaLines.push(...)      // ← RE-ENUMERATES specialists
      Effect.forkIn(scope, ...)   // ← RE-SPAWNS persona subagents
      Fiber.join(personaFiber)    // ← BLOCKS on all persona completion
    }
    handle.process({...})         // ← synthesis prompt included every turn
  }
}
```

#### Root Cause
`sensor-gate.ts:1364` `const gateResult = yield* sensorGate.classify(userText)` is called inside `runLoop` which is invoked fresh per `prompt()` call. The `step === 1` guard at `prompt.ts:1355` only prevents re-classification within the **same tool-calling loop iteration**, not across different user messages.

#### Proposed Fix: Session-Level Dispatch Cache

**Option A: SessionRunState flag (Recommended — minimal change)**

In `sensor-gate.ts`, add a module-level cache keyed on `SessionID`:

```typescript
// Track which sessions have already dispatched personas
const dispatchedSessions = new Set<SessionID>()

// In classify(), skip if already dispatched for this session
classify: Effect.fn("SensorGate.classify")(function* (prompt: string) {
  // ...existing code...
  if (dispatchedSessions.has(sessionID)) {
    return null  // Skip re-classification
  }
  dispatchedSessions.add(sessionID)
  // ...rest of classification...
})
```

Or better, use Effect's `Effect.cached` for each session:

```typescript
const classifyCache = new Map<SessionID, Effect.Effect<SensorGateResult | null>>()

function getOrCreateClassifyEffect(sessionID: SessionID, prompt: string) {
  if (!classifyCache.has(sessionID)) {
    classifyCache.set(sessionID, Effect.cached(
      // Only runs once; subsequent yields return cached result
    ))
  }
  return classifyCache.get(sessionID)!
}
```

**Option B: Workflow-driven recall (Architecture change — matches Cursor pattern)**

Instead of re-running classification on every turn, use a **hub-and-spoke pattern** where:
1. The orchestrator checks `PreviouslyExecutedDomains` before dispatching
2. Specialists are stored as **declarative agent definitions** (like Cursor's `.md` files)
3. Recall happens only when the new input requires their specific expertise
4. The orchestrator can **re-call** a specialist by providing previous output + new question

This maps directly to the Cursor/Claude Code patterns found in the research.

**Option C: Cost-gated spawning (Matches industry best practice)**

Add the 10k-token threshold check before spawning:

```typescript
if (estimatedTokens > 10_000 && !dispatchedSessions.has(sessionID)) {
  // Spawn sub-agents
} else if (estimatedTokens <= 10_000 && !dispatchedSessions.has(sessionID)) {
  // Keep in main agent context — not worth spawning
}
```

#### Confidence: HIGH
The fix is directly derived from source code analysis. The `step` variable location and the `runLoop` lifecycle are clearly visible in `prompt.ts:1150` and `prompt.ts:1146` (the `Effect.fn("SessionPrompt.run")` wrapping function).

### Vector 5: Security & Reliability Patterns 🟡 MEDIUM Confidence

#### Key Facts

1. **Sub-agent isolation is the primary security mechanism** — each sub-agent runs with its own context, tools, and file access. This limits blast radius of any single agent [1][2].

2. **Cursor's sub-agent model** includes `readonly: true` in frontmatter, preventing write access for exploration-only agents [2].

3. **Permission inheritance** is critical: Cursor's permission model merges agent-level + session-level rules. The fork (sub-agent) evaluates permissions against the **parent's** ruleset, not its own [3].

4. **Sandboxing patterns** vary by tool:
   - Claude Code: sub-agents run as fresh LLM sessions with scoped tool access
   - Cursor: sub-agents defined by markdown config, tools limited by frontmatter
   - dreamcode (current): sub-agents run via `taskTool.execute()` with `Effect.forkIn(scope)` — no explicit sandboxing

5. **The execFileSync → async issue** (Sentinel C1 in the active context) is a real reliability concern: synchronous subprocess calls block the event loop during classification.

#### Confidence: MEDIUM
Security architecture details are partially public. Dreamcode-specific analysis is from source code reading.

## Active Context: Direct Fix for dreamcode

### The Bug (Confirmed via Source Code)
- **File**: `packages/opencode/src/session/prompt.ts` line 1355
- **Guard**: `step === 1 && !session.parentID && session.mode !== "subagent"`
- **Problem**: `step` is initialized to `0` at line 1150 inside `runLoop`, which is a fresh `Effect.fn` per `prompt()` call. Every new user message gets a fresh `runLoop` with `step = 0`.
- **Impact**: `sensorGate.classify()` re-executes the Python subprocess, re-enumerates personas, re-injects `<persona-system>` blocks, and re-spawns sub-agent fibers on EVERY turn.

### Root Cause Location
```
prompt.ts:1146  Effect.fn("SessionPrompt.run")(
prompt.ts:1150    let step = 0              // ← RESETS HERE per invocation
prompt.ts:1355    if (step === 1 ...) {     // ← TRIGGERS every first iteration
prompt.ts:1364      sensorGate.classify()    // ← RE-CLASSIFIES
prompt.ts:1427      PersonaTracker.create()  // ← RE-CREATES TRACKER
prompt.ts:1477      Effect.forkIn(scope, ...)// ← RE-SPAWNS FIBERS
```

### Recommended Fix Priority

| Priority | Fix | Complexity | Impact |
|----------|-----|-----------|--------|
| **P0** | Add `Set<SessionID>` dispatch cache in SensorGate.classify | 1 hour | Eliminates re-classification entirely |
| **P0** | Store dispatched flag in `SessionRunState` | 2 hours | Persistent across crashes |

## Recommendations

### Immediate (P0 — Critical)
1. **Fix the re-dispatch bug**: Add a `Set<SessionID>` cache to `SensorGate.classify()` before the end of this session. This is a 3-line change that eliminates the primary bug.
2. **Verify with `SessionRunState`**: Check if the existing `SessionRunState` service has persistent state that could replace the in-memory cache for crash recovery.

### Short-term (P1-P2)
3. **Add cost-gated spawning**: Implement the 10k-token heuristic before spawning persona sub-agents. Only spawn when the user's prompt + context exceeds the threshold.
4. **Update the comment** at `prompt.ts:1352` to accurately state: *"Only on step 1 of this runLoop invocation (first iteration per user message). Does NOT prevent re-classification on subsequent user messages — that requires session-level dispatch tracking."*

### Long-term (P3)
5. **Migrate to declarative agent definitions**: Replace the TypeScript-encoded `PERSONA_PROFILES` array with markdown/YAML files in `.dreamcode/agents/`, matching Cursor's proven pattern.
6. **Implement hub-and-spoke orchestration**: Use the workflow engine to control agent spawning deterministically, separating orchestration from LLM execution.
7. **Add `PreviouslyExecutedDomains` tracking**: Before re-calling a specialist, check what they produced previously and whether the new input requires their specific expertise. Only re-call if the delta warrants it.
